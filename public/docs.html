Run Migrations

Execute all ten migration files in numbered order. Migration 010 seeds all 35 permissions and assigns them to the four default roles.

Shell
# SQLite — run each migration file
for f in database/migrations/*.sql; do
  sqlite3 database/db.sqlite < "$f"
done

# MySQL
for f in database/migrations/*.sql; do
  mysql -u root etus < "$f"
done

Request Lifecycle

Every HTTP request passes through the same pipeline:

public/index.php → Router → Middleware → Controller → Model → View / JSON

Middleware tokens applied per-route: auth enforces login, guest redirects logged-in users, csrf validates the _token field on all POST requests.

Base Model

All models extend Etus\Framework\Database\Model which provides find(), findOrFail(), all(), create(), update(), delete(), where(), and automatic timestamp + audit field management.

Encryption

Every message is encrypted before storage. The raw ciphertext (body_enc) is never returned to the client — decryption happens server-side before the JSON response is built.

PHP — Encryption (ChatMessage::encrypt)
// Key derivation — HMAC-SHA256 of the APP_CHAT_KEY env var
$key = hash_hmac('sha256', APP_CHAT_KEY, 'etus-chat-v1', true);

// Unique 12-byte IV per message
$iv  = random_bytes(12);
$tag = '';

$cipher = openssl_encrypt(
    $plaintext, 'aes-256-gcm', $key,
    OPENSSL_RAW_DATA, $iv, $tag
);

// Stored: base64(iv[12] + tag[16] + ciphertext)
$stored = base64_encode($iv . $tag . $cipher);

Real-Time Polling

The chat client polls /api/chat/{roomId}/poll?after={lastMsgId} every 3 seconds. The server returns only messages with id > lastMsgId, auto-marks them as read, and returns the updated unread count. Smart scroll logic prevents force-scrolling when the user has scrolled up to read history.

JavaScript — Poll loop
// Started on DOMContentLoaded, cleared on beforeunload
async function pollMessages() {
  const res  = await fetch(`/api/chat/${ROOM_ID}/poll?after=${lastMsgId}`);
  const data = await res.json();

  data.messages.forEach(msg => {
    if (msg.sender_id !== MY_ID) renderMessage(msg, false);
    lastMsgId = Math.max(lastMsgId, msg.id);
  });

  if (data.messages.length > 0 && isAtBottom) scrollToBottom(true);
}

setInterval(pollMessages, 3000);

Using the Gate in Controllers

PHP
// In any controller or view:
if (! Gate::can('edit-missions')) {
    return redirect('/dashboard');
}

// Check role (bypasses permission lookup for super_admin)
if (Gate::hasRole('super_admin')) { ... }

// Helper functions (views + controllers)
can('view-reports')       // bool
cannot('delete-users')    // bool
can_any(['edit-tasks', 'edit-missions'])  // bool
has_role('manager')       // bool
has_any_role(['admin', 'super_admin'])  // bool

// In Blade-style PHP views:
<?php if (can('create-missions')): ?>
  <a href="/missions/create">New Mission</a>
<?php endif; ?>
Live Cache Flush When permissions are changed via the admin panel, Gate::flushCache() is called automatically inside Role::syncPermissions(), Role::addPermission(), and Role::removePermission(). Permission changes take effect on the next request without requiring users to log out.

REST API Reference

All API endpoints return application/json. Successful responses follow the envelope {"success":true,"message":"...","data":{}}. Authentication is session-based — send cookies with each request.

CSRF on API routes API controllers do NOT apply the csrf middleware. CSRF is enforced only on web POST routes. XHR/fetch requests from the front-end should include the X-Requested-With: XMLHttpRequest header. The meta[name="csrf-token"] tag in the layout provides the token for POST bodies when needed.

Standard Response Shape

JSON
// Success
{ "success": true, "message": "OK", "data": { ... } }

// Error
{ "success": false, "message": "You are not authorised.", "data": {} }

// HTTP status codes used:
// 200 — success
// 400 — validation error
// 403 — unauthorised (not a participant, wrong role)
// 404 — resource not found
// 500 — server error

Security

A summary of every security mechanism in the platform.

MechanismWhere AppliedDetails
AES-256-GCMChat messagesKey derived via HMAC-SHA256. Unique 12-byte IV per message. 16-byte GCM authentication tag detects tampering. Raw blob never sent to client.
CSRF TokensAll POST web routesDouble-submit pattern via CsrfMiddleware. Token validated before any controller action.
Password HashingRegistration, password resetpassword_hash() with PASSWORD_DEFAULT (bcrypt). Verified with password_verify().

Core Tables

SQL — Chat Tables (Migration 010)
CREATE TABLE chat_rooms (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  type        TEXT    NOT NULL,              -- team|direct|command
  name        TEXT    NOT NULL,
  team_id     INTEGER REFERENCES teams(id),
  mission_id  INTEGER REFERENCES missions(id),
  is_active   INTEGER NOT NULL DEFAULT 1,
  created_at  TEXT, updated_at TEXT
);

CREATE TABLE chat_messages (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  room_id     INTEGER NOT NULL REFERENCES chat_rooms(id),
  sender_id   INTEGER NOT NULL REFERENCES users(user_id),
  msg_type    TEXT    NOT NULL DEFAULT 'text',
  body_enc    TEXT    NOT NULL,             -- AES-256-GCM ciphertext
  body_preview TEXT,                        -- First 72 chars unencrypted
  parent_id   INTEGER REFERENCES chat_messages(id),
  is_deleted  INTEGER DEFAULT 0,
  edited_at   TEXT, created_at TEXT
);
body_preview The first 72 characters of each message are stored unencrypted in body_preview to allow room list last-message previews without decrypting the full message. This is intentional — previews are safe for operational context. Set to NULL for any message content you never want previewed.
